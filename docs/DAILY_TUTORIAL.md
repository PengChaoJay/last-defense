# 《最后的防线》30 天逐日开发教程

这份教程按照“每天约 1.5～2.5 小时”的节奏设计。目标不是机械复制最终代码，而是理解一个个人游戏项目如何从空白工程走到可公开试玩的 Demo。

如果你直接学习现有仓库，可以把每天的任务理解为阅读顺序和改造练习；如果你从零重做，可以按天逐步实现。

## 使用方式

每天遵循同一流程：

1. 阅读当天目标。
2. 只实现当天列出的功能。
3. 在 Godot 中运行并完成验收。
4. 提交一次 Git 记录。
5. 将遇到的问题写进当天提交或开发日志。

推荐提交格式：

```text
feat: day 01 initialize Godot project
fix: day 08 prevent projectile double hit
docs: day 30 prepare GitHub release notes
```

# 第一阶段：做出战斗闭环

## Day 1：创建工程与版本库

### 目标

建立可以运行、可以提交、可以恢复的 Godot 工程。

### 操作

1. 使用 Godot 4.7 创建 `last-defense` 项目。
2. 选择 Compatibility 渲染器。
3. 设置窗口为 1280×720。
4. 创建 `main.tscn`，根节点使用 `Node2D`。
5. 为根节点挂载 `main.gd`。
6. 初始化 Git，加入 `.gitignore`、`.editorconfig` 和 `.gitattributes`。

### 学习重点

- `project.godot` 是项目配置入口。
- `.godot/` 是本地导入缓存，不应提交。
- 每天只做小提交，方便回滚。

### 验收

- 项目能显示空窗口。
- 关闭并重新打开后仍能运行。
- `git status` 不包含 `.godot/`。

## Day 2：绘制玩家与处理移动

### 目标

让玩家能用 WASD 和方向键移动。

### 操作

1. 在输入映射中配置 `move_left/right/up/down`。
2. 创建 `player_pos`、`player_speed` 和碰撞半径。
3. 在 `_process(delta)` 中读取 `Input.get_vector()`。
4. 用速度乘以 `delta`，保证不同帧率下移动速度一致。
5. 在 `_draw()` 中先用圆形代表玩家。
6. 使用 `clamp()` 限制玩家在屏幕内。

### 对应代码

- `update_player()`
- `_draw()` 中的玩家绘制部分

### 验收

- 四个方向移动正常。
- 斜向速度不会比横向更快。
- 玩家不会离开屏幕。

## Day 3：生成敌人并追踪目标

### 目标

让敌人从屏幕边缘持续出现并追踪玩家。

### 操作

1. 用数组保存敌人字典。
2. 每个敌人记录位置、生命、速度、半径和伤害。
3. `spawn_enemy()` 随机选择屏幕四边。
4. 每帧计算 `(target - position).normalized()`。
5. 使用 `spawn_timer` 控制生成频率。

### 对应代码

- `spawn_enemy()`
- `update_spawning()`
- `update_enemies()`

### 验收

- 敌人会从不同方向出现。
- 所有敌人都会朝玩家移动。
- 运行两分钟没有数组越界错误。

## Day 4：自动索敌与能量弹

### 目标

实现最基本的自动战斗。

### 操作

1. 遍历敌人，使用距离平方寻找最近目标。
2. 创建子弹字典：位置、速度、寿命、伤害。
3. 到达攻击冷却后发射。
4. 每帧移动子弹并减少寿命。
5. 子弹超时后从数组删除。

### 对应代码

- `update_shooting()`
- `update_bullets()`

### 验收

- 有敌人时自动射击。
- 没有敌人时不浪费子弹。
- 子弹始终朝发射时的目标方向飞行。

## Day 5：伤害、死亡和接触攻击

### 目标

让战斗产生明确结果。

### 操作

1. 检查子弹与敌人的圆形距离。
2. 命中时减少敌人生命。
3. 敌人死亡时安全地倒序删除。
4. 敌人接触玩家时造成伤害。
5. 使用 `hit_cd` 避免每帧连续扣血。
6. 玩家生命归零时进入结算状态。

### 对应代码

- `damage_enemy()`
- `update_enemies()`

### 验收

- 子弹能消灭敌人。
- 玩家不会因为一次接触在一帧内直接归零。
- 死亡后战斗停止。

## Day 6：能源核心与双重失败条件

### 目标

加入真正符合“最后的防线”的守护目标。

### 操作

1. 在地图中央创建能源核心。
2. 给核心设置独立生命值。
3. 敌人距离玩家较近时攻击玩家，否则攻击核心。
4. 玩家或核心任意一个生命归零都失败。
5. 在 HUD 中显示两条生命值。

### 设计思考

玩家不能只绕着地图边缘逃跑，因为核心会失守。

### 验收

- 敌人会根据距离切换目标。
- 核心受到攻击时生命下降。
- 两种失败条件都能进入结算。

## Day 7：第一周整合与试玩

### 目标

得到第一份“移动—攻击—死亡—重开”闭环。

### 操作

1. 增加标题、计时、击杀数和结算文字。
2. 增加 `R` 重开。
3. 清理所有运行时错误。
4. 导出或让至少三个人试玩三分钟。

### 本周停止线

如果这一天仍无法完整重开，不要制作新武器或美术，先修复闭环。

### 验收

- 能连续玩三分钟。
- 死亡后无需重启程序即可再开一局。
- 试玩者能理解“保护核心”。

# 第二阶段：成长与构筑

## Day 8：经验晶体与拾取

### 目标

给击杀增加成长回报。

### 操作

1. 敌人死亡时生成经验晶体。
2. 晶体进入拾取范围后向玩家飞行。
3. 接触玩家后增加经验并删除晶体。
4. 在 HUD 显示等级和经验条。

### 对应代码

- `xp_orbs`
- `update_xp_orbs()`
- `gain_xp()`

### 验收

- 经验不会隔空直接获得。
- 拾取范围能明显观察到。
- 经验达到要求后只升级一次。

## Day 9：升级三选一

### 目标

实现 Roguelite 的核心决策界面。

### 操作

1. 创建升级配置数组。
2. 升级时随机抽取三项。
3. 暂停战斗更新，但继续绘制界面。
4. 用数字键选择升级。
5. 应用效果后恢复战斗。

### 对应代码

- `upgrades`
- `open_upgrade_menu()`
- `choose_upgrade()`
- `draw_upgrade_menu()`

### 验收

- 三张卡不阻挡输入。
- 选择后对应属性发生变化。
- 选择期间敌人和子弹停止移动。

## Day 10：基础属性升级

### 目标

完成伤害、射速、移速、装甲、磁力和多重射击。

### 操作

逐项实现并实际验证，不要一次写完后只看代码：

- Damage：观察伤害数字。
- Fire Rate：观察射击间隔。
- Mobility：比较移动速度。
- Armor：检查最大生命和恢复。
- Magnet：观察经验吸附范围。
- Multishot：观察弹道数量和夹角。

### 验收

六种升级均有肉眼可见效果。

## Day 11：电弧模块

### 目标

制作第二种武器，形成群体伤害路线。

### 操作

1. 设置独立的 `arc_timer`。
2. 找到范围内最近目标。
3. 记录已命中的目标，防止重复弹射。
4. 每跳降低或维持伤害。
5. 用短寿命线段绘制闪电。

### 对应代码

- `update_arc_weapon()`
- `arc_effects`
- `update_arc_effects()`

### 验收

- 电弧不会无限弹射。
- 没有目标时不会报错。
- 等级提高后弹射次数或频率增加。

## Day 12：环绕刀片

### 目标

制作第三种武器，形成近战防守路线。

### 操作

1. 使用角度和 `Vector2.from_angle()` 计算刀片位置。
2. 多刀片在圆周上均匀分布。
3. 为每个敌人设置刀片受击冷却。
4. 检测刀片与敌人圆形距离。

### 对应代码

- `update_orbit_weapon()`
- `_draw()` 中的刀片绘制

### 验收

- 刀片围绕玩家平滑旋转。
- 同一敌人不会每帧承受刀片伤害。
- 多刀片间距均匀。

## Day 13：武器融合

### 目标

让升级组合产生质变，而不是只有数值增长。

### 操作

1. 记录伤害、射速和多重射击选择次数。
2. 用 `refresh_fusions()` 检查条件。
3. 实现连锁脉冲。
4. 实现过载旋刃。
5. 在 HUD 显示已激活融合。

### 验收

- 条件不足时不会误触发。
- 满足条件后立即激活。
- 两种融合可以同时存在。

## Day 14：敌人分层与中期平衡

### 目标

加入快速和重型敌人，形成不同走位压力。

### 操作

1. 快速敌人：低生命、高速度、低伤害。
2. 重型敌人：高生命、低速度、高伤害。
3. 根据时间逐步解锁敌人类型。
4. 让生命和生成频率随时间增长。

### 验收

- 玩家能从轮廓和颜色判断敌人类型。
- 快速敌人迫使玩家移动。
- 重型敌人迫使玩家提高输出。

# 第三阶段：完整关卡与 Boss

## Day 15：机械柱与碰撞

### 目标

打破空旷竞技场绕圈玩法。

### 操作

1. 放置六个圆形机械柱。
2. 玩家进入柱体时沿法线推出。
3. 敌人接近柱体时添加排斥向量。
4. 最后执行穿透修正。

### 对应代码

- `obstacles`
- `resolve_player_obstacles()`
- `steer_around_obstacles()`
- `resolve_enemy_obstacle()`

### 验收

- 玩家不能穿过柱体。
- 敌人会从柱体两侧绕行。
- 敌人不会长时间卡在柱体内部。

## Day 16：危险区域

### 目标

让地图不同位置具有不同风险。

### 操作

1. 创建腐蚀区并按固定间隔扣血。
2. 创建干扰区并降低移动速度。
3. 用颜色、圆环和动画明确表达边界。
4. 确保效果只在区域内生效。

### 验收

- 玩家能在进入前识别危险。
- 离开区域后效果立即停止。
- 危险区不会直接覆盖核心。

## Day 17：互动终端

### 目标

让玩家主动离开核心冒险获取收益。

### 操作

1. 放置维修、超载和医疗终端。
2. 检测玩家是否进入互动范围。
3. 显示 `E` 提示。
4. 应用效果并启动冷却。
5. 用圆环显示冷却进度。

### 对应代码

- `terminals`
- `activate_nearby_terminal()`
- `draw_terminal_prompt()`

### 验收

- 玩家不靠近终端时无法隔空使用。
- 冷却期间不能重复触发。
- 三类终端效果均有明确反馈。

## Day 18：随机事件与精英敌人

### 目标

提高每局节奏的不确定性。

### 操作

1. 每隔随机时间触发事件。
2. 实现核心突袭。
3. 实现精英入侵。
4. 实现终端重置。
5. 给精英更高生命、伤害和经验价值。

### 对应代码

- `event_timer`
- `trigger_random_event()`
- `spawn_enemy(true)`

### 验收

- 同一局能够出现不同事件。
- 事件有醒目的系统提示。
- 精英敌人死亡给予更多经验。

## Day 19：Boss 基础行为

### 目标

建立最终战。

### 操作

1. 第 7 分钟生成 Boss。
2. 设置独立生命、半径、伤害和速度。
3. 添加 Boss 生命条。
4. 定时召唤三只普通敌人。
5. Boss 死亡时立即胜利。

### 验收

- Boss 只生成一次。
- Boss 生命条正确同步。
- 召唤不会破坏敌人数组遍历。

## Day 20：Boss 冲锋与预警

### 目标

让 Boss 攻击可读、可躲，而不是无提示伤害。

### 操作

1. 冲锋前锁定方向。
2. 显示闪烁预警线。
3. 预警结束后高速移动一段时间。
4. 冲锋后进入冷却。
5. 处理冲锋与障碍物的碰撞。

### 验收

- 玩家看到预警后有时间躲开。
- 冲锋方向不会中途追踪玩家。
- Boss 不会冲出地图永久消失。

## Day 21：完整一局与节奏调整

### 目标

打通标题到胜利的完整流程。

### 操作

1. 确认第 7 分钟 Boss 出现。
2. 设置第 10 分钟超时失败。
3. 完整玩一局并记录每分钟压力。
4. 调整升级速度、敌人频率和 Boss 生命。

### 验收

- 能从标题页进入游戏并最终胜利或失败。
- 暂停、升级和结算不会互相冲突。
- 一局没有阻断流程的错误。

# 第四阶段：表现、素材与测试

## Day 22：战斗反馈

### 目标

让命中、受伤、拾取和升级都有明确反馈。

### 操作

1. 增加伤害数字。
2. 增加受击闪白。
3. 增加屏幕震动并让它快速衰减。
4. 增加低生命警告边框。
5. 增加系统提示横幅。

### 验收

- 玩家能立即判断是否命中。
- 震动不会长时间影响阅读。
- 低生命状态足够明显但不遮挡游戏。

## Day 23：标题、暂停和结算界面

### 目标

让陌生玩家无需编辑器说明也能开始和结束游戏。

### 操作

1. 增加标题界面和操作提示。
2. 使用 `Enter` 开始。
3. 使用 `Esc` 暂停和继续。
4. 完善胜利、失败和重开界面。
5. 避免暂停状态继续更新时间。

### 验收

- 玩家第一次打开就知道如何开始。
- 暂停时战斗完全停止。
- 结算后能稳定重开。

## Day 24：音效

### 目标

为主要动作补充声音反馈。

### 操作

1. 准备射击、命中、受伤、拾取、升级、Boss 和胜利音效。
2. 创建 `AudioStreamPlayer`。
3. 控制不同音效音量。
4. 增加 `M` 静音。
5. 避免高频音效过于刺耳。

### 仓库工具

```bash
python tools/generate_audio.py
```

### 验收

- 七类音效均能触发。
- 静音开关有效。
- 连续射击时音效不会压过所有声音。

## Day 25：角色和敌人素材

### 目标

用统一风格的贴图替换基础圆形。

### 操作

1. 准备透明背景的玩家、敌人、Boss 和核心 PNG。
2. 保留原始高清图。
3. 裁切成正方形并缩放到 256×256。
4. 在代码中加载 `Texture2D`。
5. 保持碰撞半径与图片视觉尺寸协调。

### 仓库工具

```powershell
Godot.exe --headless --path . --script res://tools/prepare_sprites.gd
```

### 验收

- 图片透明边缘正常。
- 小尺寸下仍能区分类型。
- 替换素材不改变碰撞和数值。

## Day 26：UI 与可读性检查

### 目标

保证复杂战斗时仍能读懂关键信息。

### 操作

1. 检查玩家、核心、Boss 和经验条。
2. 检查升级卡文字是否越界。
3. 检查融合状态、终端提示和倒计时。
4. 降低不重要元素的亮度。
5. 用颜色固定信息含义。

### 验收

- 玩家不暂停也能看到核心生命。
- Boss、危险区和终端颜色不会混淆。
- 1280×720 下所有文字完整显示。

## Day 27：自动测试与回归

### 目标

用自动测试保护关键系统。

### 操作

1. 实例化主场景。
2. 强制激活两种融合。
3. 强制生成精英和 Boss。
4. 激活武器终端。
5. 验证障碍和终端数量。

### 命令

```powershell
Godot_console.exe --headless --path . --script res://tests/smoke_test.gd
```

### 验收

输出包含：

```text
SMOKE_TEST_OK
```

## Day 28：性能和长时间测试

### 目标

确认完整一局不会因对象堆积而严重卡顿。

### 操作

1. 打开 Godot Profiler。
2. 观察敌人、子弹、经验和粒子数量。
3. 检查每帧索敌开销。
4. 检查删除数组元素时是否出现错误。
5. 在目标电脑完整玩两局。

### 验收

- 1080p 下尽量维持 60 FPS。
- 重开后旧敌人、音效和特效被清空。
- 第二局性能不会明显低于第一局。

## Day 29：外部试玩

### 目标

用真实行为验证游戏，而不是只听“挺好玩”。

### 操作

邀请 5～10 名玩家，记录：

- 是否能独立开始游戏。
- 第一局存活时间。
- 是否主动开始第二局。
- 使用了哪些武器和终端。
- 死亡原因是否清楚。
- 哪一分钟开始觉得重复。

### 验收

- 至少 80% 玩家不需要口头教学。
- 至少 30% 玩家主动再开一局。
- 所有阻断流程的 Bug 都被记录。

## Day 30：GitHub 与 Demo 发布准备

### 目标

让陌生人能理解、下载和运行项目。

### 操作

1. 完善 `README.md`。
2. 检查架构、玩法和教程文档。
3. 添加截图和短视频。
4. 选择并添加许可证。
5. 运行自动测试。
6. 清理缓存、日志和不应公开的文件。
7. 创建 `v0.1.0` 标签和 Release 说明。
8. 上传 Windows Demo 压缩包。

### 验收

- 新用户只读 README 就能运行。
- 仓库不包含密码、个人数据和单位内部资产。
- Release 包不要求安装 Godot。
- Issue 页面写明已知问题和反馈格式。

---

# 每周复盘模板

每七天回答以下问题：

1. 本周真正完成了什么可运行成果？
2. 哪个功能花费时间最多，为什么？
3. 玩家行为和我的预期有什么不同？
4. 哪个功能应该删除或推迟？
5. 下周唯一最重要的验收结果是什么？

# 最后提醒

30 天计划的价值不是保证做出商业成功游戏，而是建立一条可以重复的路径：

```text
提出机制 → 做出原型 → 完成闭环 → 找人试玩 → 根据证据决定继续或停止
```

不要因为某一天没有完成全部任务就推翻项目。优先缩小当天范围，始终保持工程处于可运行状态。
